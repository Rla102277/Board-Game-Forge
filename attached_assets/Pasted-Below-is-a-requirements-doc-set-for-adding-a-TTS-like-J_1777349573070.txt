Below is a requirements doc set for adding a TTS-like JSON-driven tabletop simulator to your existing app.

I’m calling it TTS Runtime in the docs, but internally I would name it something like:

Tabletop Runtime
JSON Game Runtime
Prototype Tabletop Engine
Game Lab Runtime

Because “TTS” can confuse people with text-to-speech.

⸻

Requirement Doc Set: JSON-Driven Tabletop Runtime

1. Product Requirements Document

Product Name

Tabletop Runtime

Purpose

Add an embedded tabletop simulator-style experience to the existing app that allows users to load a structured game definition in JSON and instantly render a playable multiplayer board/card game inside the app.

The system should support rapid multiplayer prototyping for tabletop games, card games, board games, deck-builders, tactical games, and hybrid tabletop concepts.

Product Vision

The user should be able to:

Create or generate a game definition
↓
Load JSON into the app
↓
See a playable table appear
↓
Invite other players
↓
Playtest the game
↓
Record actions and feedback
↓
Revise the JSON
↓
Replay or test again

Long-term, the system becomes a board-game design workbench where AI can generate rules, cards, decks, boards, and setup scripts, then the runtime spins them up into playable prototypes.

⸻

2. Core User Stories

Game Designer

As a game designer, I want to upload or generate a JSON game definition so that I can instantly test a board/card game concept without building a custom app for every prototype.

Acceptance Criteria

* User can create a new prototype.
* User can attach or paste JSON.
* System validates the JSON.
* System renders a table from the JSON.
* User can interact with cards, decks, tokens, zones, and player areas.
* User can save the prototype.

⸻

Playtester

As a playtester, I want to join a game room from a link so that I can test the prototype with other players.

Acceptance Criteria

* User can join a multiplayer room.
* User is assigned a player seat.
* User can only see private information that belongs to them.
* User sees public game state in real time.
* User can take allowed actions on their turn.
* User can leave and rejoin the room.

⸻

Game Creator With AI

As a creator, I want AI to generate game JSON so that I can rapidly test new game ideas.

Acceptance Criteria

* AI-generated JSON must conform to schema.
* Invalid JSON produces clear validation errors.
* User can preview the generated game before starting a multiplayer session.
* User can edit JSON and re-render the table.

⸻

Admin / Developer

As a developer, I want the tabletop runtime to be modular so that new component types and game actions can be added without rewriting the whole system.

Acceptance Criteria

* Renderer, rules engine, schemas, and multiplayer engine are separated.
* New tabletop object types can be registered.
* New action types can be added through action resolvers.
* Runtime state remains JSON-serializable.

⸻

E. Game Engine Adapter

Responsible for converting the JSON game definition into a boardgame.io game object.

Responsibilities

Run setup actions
Register generic moves
Resolve turn order
Resolve phases
Validate moves
Apply effects
Update game state
Emit action log entries

Core Adapter Function

createGameFromDefinition(gameDefinition)

Example

export function createGameFromDefinition(definition) {
  return {
    name: definition.game.id,
    setup: ({ ctx }) => {
      return setupInitialState(definition, ctx);
    },
    moves: {
      drawCard: ({ G, ctx, playerID }, args) => {
        return resolveMove(G, ctx, playerID, {
          type: "drawCard",
          ...args
        });
      },
      moveCard: ({ G, ctx, playerID }, args) => {
        return resolveMove(G, ctx, playerID, {
          type: "moveCard",
          ...args
        });
      },
      endTurn: ({ events }) => {
        events.endTurn();
      }
    }
  };
}

F. Rules Engine

Responsible for determining whether a player action is legal and applying its effects.

Responsibilities

Check current player
Check phase
Check card ownership
Check zone permissions
Check resource costs
Check target legality
Apply action effects
Update game state
Record action log
Return success or error

Rule Engine Principle

The UI must never directly mutate final game state.

Correct pattern:

User tries action
↓
UI sends action request
↓
Engine validates action
↓
Engine updates state
↓
Renderer redraws state

Incorrect pattern:

User drags card
↓
UI moves card directly
↓
State is assumed valid

Performance

Runtime should support 2-6 players in MVP
Runtime should support at least 300 cards in definition
Runtime should support at least 100 visible tabletop objects
State updates should feel near real-time for turn-based play
Card dragging should be smooth on desktop

Security

Players cannot see hidden cards through client state
Players cannot call illegal moves directly
Server validates all moves
Prototype ownership is enforced
Only invited users can join private rooms

Reliability

Players can refresh and rejoin
Game state persists during active match
Action log records all successful moves
Invalid actions return readable errors

Maintainability

Renderer components must be modular
Game engine must be separate from UI
Schemas must be versioned
Runtime state must remain JSON-serializable
Generic actions must be reusable across games

17. Prompt for Coding Agent

Use this as the opening prompt for your app-building agent.

You are adding a JSON-driven tabletop runtime to an existing React/TypeScript app.
Goal:
Build a 2D Tabletop Simulator-like runtime that can load a game definition from JSON, validate it, render a playable board/card game inside the app, and support multiplayer playtesting through boardgame.io.
Architecture rules:
- Keep static game definitions in /data or persisted prototype records.
- Keep schemas in /schemas.
- Keep rendering components in /tabletop-runtime.
- Keep game logic in /game-engine.
- Do not mix UI state with authoritative game state.
- The UI may request actions, but the game engine must validate and resolve them.
- Runtime state must remain JSON-serializable.
- Start with cards, decks, zones, hands, discard piles, tableaus, simple tokens, and basic dice.
- Do not build 3D physics.
- Do not build a universal scripting language yet.
- Implement generic actions first: shuffleDeck, dealCards, drawCard, moveCard, discardCard, revealCard, flipCard, moveToken, rollDie, gainResource, spendResource, endTurn.
- Use boardgame.io for turn-based multiplayer state.
- Use dnd-kit for drag/drop interactions.
- Add JSON validation before rendering.
- Add clear validation errors for broken references.
MVP:
1. Load a sample game JSON.
2. Validate the JSON.
3. Render the tabletop.
4. Start a local game.
5. Draw, play, discard, and move cards.
6. End turn.
7. Add boardgame.io state management.
8. Add two-player multiplayer.
9. Enforce private hand visibility.
10. Record an action log.
First test game:
Build a simple two-player card game called Draw and Score. Players draw numbered cards, play them to their tableau, and highest score wins when the deck is empty.
Do not rewrite the whole app. Add this as a modular feature.
Before coding, inspect the existing app structure and propose a small-file implementation plan.

18. Blunt Build Guidance

The most important decision: do not build a full Tabletop Simulator clone.

Build this:

JSON-driven
2D
Turn-based
Card/board focused
Multiplayer
AI-generatable
Schema-validated

Not this:

3D
Physics-heavy
Steam Workshop clone
Universal sandbox
Rules engine that can model every game ever made

Your MVP should prove one thing:

Can a JSON file create a playable multiplayer tabletop prototype inside my app?

Everything else is later.
